# 多源待办总控

<!-- skill-workflow-link -->
[查看完整流程图与操作说明](references/workflow.md)
<!-- /skill-workflow-link -->

团队首次使用先读 [配置与依赖](references/team-setup.md)；已有配置与本轮明确入口直接复用，不重复索取。

把学生群、学生私聊、老师／班主任／导师协作聊天和当前服务台账对成一份可执行待办。核心不是“多找几条消息”，而是证明哪些学生、渠道和时间范围已覆盖，哪些仍是缺口。

## 边界与分流

- 默认只读：不发消息、不改聊天、不更新飞书、不替用户承诺服务或恢复服务。
- 若用户要求客户、合同、财务、招聘等全域个人总控，同时使用 `personal-todo-control`；本技能只负责学生服务的多聊天源完整性。
- 涉及本地微信检索时，优先使用当前使用者自行配置、已授权的聊天连接器或本地导出；若已安装 `yichen-wechat-local-vault`，可使用它。默认只读现有可访问快照并记录解析／缓存截止时间，再按身份和时间窗口检索；不自动提取密钥、解密或增量刷新。只有用户当前或会话已有明确刷新授权时，按本轮最小账户／时间范围刷新并核对结果；不要把 Computer History 或界面摘要当成聊天正文。
- 涉及飞书时优先用当前可用的 `lark-cli` 动态解析和读取；历史 token、截图和旧摘要只作线索。

## 先锁定本轮合同

来源优先用本次材料；未给入口时按成员私有配置 `feishu.service_base_url` 定位当前服务主表、按 `workspace.student_root` 定位本地交付。聊天连接器或导出由成员提供并授权。缺少来源时保留覆盖缺口，不读取作者历史源。全域个人总控使用 `personal-todo-control`；未安装时只完成本技能学生范围并说明边界。

开工前写清：`资料截止时间`、`计划适用日期`、`学生范围`、`聊天时间窗`、`预期来源`、`缓存／解析截止时间`、`新鲜度缺口`、`写入与刷新权限`。学生范围默认来自当前人工维护的服务主表，再补入聊天中新出现但尚未匹配的身份。

把人工维护的服务主表视为服务状态、Offer、在册名单和人工标记的权威来源。新聊天可以增加进展、风险、请求、期限和核实动作，但不能静默覆盖主表状态。

## 建立“学生 × 来源”覆盖矩阵

每位在范围内的学生至少核对以下来源：服务主表、学生群、学生私聊、相关协作聊天；若任务涉及作品集，再核对学员索引／规划页和真实交付记录。

每个格子只能使用这些覆盖状态：

| 状态 | 含义 |
|---|---|
| 已覆盖 | 正文可读，时间窗已检查 |
| 部分覆盖 | 只读到附件、语音触点、截断正文或不完整时间窗 |
| 未检查 | 没有证据表明本轮实际检索过该来源 |
| 无匹配会话 | 已检索但无法把会话唯一匹配到该学生 |
| 读取失败 | 已定位来源，但工具或索引失败 |
| 不适用 | 有直接证据证明该来源不属于此学生 |

“没有提供”必须写成“未检查”；“没搜到”只有在真实检索后才能写成“无匹配会话”。两者都不能写成“无待办”。“部分覆盖”也必须有实际读到的内容，不能用来包装尚未检查的来源。快照截止早于本轮时间窗、截止不明或数据源不可访问时，标注新鲜度缺口，受影响格子为部分覆盖／未检查；不能声称核对了最新消息，也不能为补齐覆盖默认刷新。先写覆盖状态，再判断事项。报告 `应检查格子数／已覆盖／部分覆盖／未检查／无匹配／失败／不适用`；联系人未知的故障群单独计数。

## 从消息生成待办

识别明确请求、用户承诺、团队接单、硬时间、等待、风险和关闭证据。按 `学生 + 交付对象 + 下一动作` 去重；同一事项在群聊、私聊和协作聊天重复出现时合并为一项，并保留全部关键证据。

每项至少包含：学生、动作、责任人、硬时间或 `Open`、状态、证据来源与时间、完成标准。建议时间必须标为“建议”，不能冒充承诺截止。

| 证据 | 正确判断 |
|---|---|
| 学生在群里提出真实问题，团队无人实质回复 | 默认用户兜底：回复或明确分配 |
| 用户在私聊承诺“明天给” | 已承诺未交付；以真实交付关闭 |
| 协作方明确说“我来处理” | 已委派；用户只盯结果和检查点 |
| 只有转发、`@`、收到、好的 | 不算接单或完成 |
| 只能看到语音／附件触点 | 语义 `Open`，生成最小核实动作 |
| 聊天与服务状态冲突 | 主表状态不变，新增人工核实／回填动作 |

## 作品集缺口必须拆成两个判断

分别判断：

1. `作品集需要`：已确认需要／可能需要／暂无证据。
2. `规划状态`：未规划／已规划待启动／进行中／已交付／Open。

项目栏空白、目标岗位名称或通用岗位知识都不能单独证明“需要作品集且尚未规划”。只有学生请求、明确岗位要求、已确认服务策略或可回读规划证据才能升级判断。输出分为“已确认需要且未规划”和“待核实候选”，不要混成一个名单。

## 输出与验收

读取 [references/evidence-and-output-contract.md](references/evidence-and-output-contract.md)，按其中的字段、结构和示例交付。

交付前确认：

- 服务主表中的每位范围内学生都进入覆盖矩阵，没有只扫描活跃聊天。
- 学生群、私聊和协作聊天分别核对，内部协作承诺没有漏并且没有冒充学生确认。
- 同一事项已跨来源去重，责任人和完成标准可执行。
- 无法读取或缓存未覆盖截止时间的来源明确标成缺口，并给出最小核实／授权刷新动作；本轮没有刷新时如实报告所用快照时间。
- 没有检索证据的来源标成“未检查”，没有误写成“部分覆盖”或“无匹配”。
- 作品集需要与规划状态分开，空白字段没有被直接推断。
- 标题或摘要明确写“完整覆盖”或“部分覆盖”；存在任何未知联系人、部分覆盖、未检查、无匹配会话或读取失败时，不得称为全量完成。

## 常见错误

- 只列“读过哪些应用”，不对账学生和渠道。
- 只扫学生群，漏掉用户在私聊中的承诺和协作方的接单。
- 把“已发送”当成对方验收，把“收到”当成交付完成。
- 用旧摘要、Computer History 或聊天列表标题代替当前聊天正文。
- 为了给出完整名单而猜测身份、截止时间、作品集需要或服务状态。
