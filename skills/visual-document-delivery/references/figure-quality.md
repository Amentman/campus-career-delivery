# 成图质量：理解、设计与显示分开验收

## 先确定图要完成的讲解

每张图的设计稿先写清四项：读者看完要回答的问题；必须看见的关系；主阅读路径；细节放回哪段正文。图的标题必须与实际结构一致：标题说三层，图中就应能辨认三层及层间关系。用五行清单代替三层结构，属于含义不匹配。

按内容选视觉语法。业务场景可以用场景剖面加交付路线；经历与岗位用证据映射；程序处理用数据流；取舍用分支树；实验用对照与隔离；排障用故障树与恢复条件。比较表本身有效时保留原生表格，不必再截图成一张“图”。插画用于说明真实对象或区别，不用插画掩盖错误逻辑。

## 嵌入前的成图检查

将成图缩到最终正文的显示宽度，按下表逐图写具体观察。

| 检查 | 要回答的问题 |
| --- | --- |
| 图意 | 标题承诺的解释是否真的在画面里？哪些对象、动作或关系帮助读者回答问题？ |
| 逻辑 | 每条线的起止、方向和含义是什么？权限先于读取，异常覆盖对应步骤，判断分支与终态是否完整？ |
| 层级 | 第一眼看哪里，接着沿什么路径阅读？主线、辅助说明和例外是否有明确区别？ |
| 可读性 | 在实际宽度、正常缩放下能否直接读关键标签？空间是否拥挤，或因留白过大而削弱关系？ |
| 视觉作用 | 图比相邻正文多解释了什么？拿掉框线与箭头后若只剩同义段落，改成真正的关系图或原生文字／表格。 |

五项均有具体观察且没有未解决问题，才能将该图判为通过。文字正确、排列整齐、文件高清、图片显示成功，只能证明各自检查项，不能替代这个判断。不得仅用“清晰、美观、已检查”作观察。

逻辑必须正确，设计也必须达到正式阅读材料的水平。把全文缩进等大框、反复使用同一张表格式构图、仅换颜色与圆角，不构成设计改进；但流程确实相同的节点可以保持一致，不为了变化破坏含义。整体审稿时把全部讲解图放在一起检查：重点、字号层级、配色含义一致，构图服从各图关系，不机械复制同一版式。

文档讲解图、流程图、关系图和方法总览默认直接使用 GPT Image 2（`gpt-image-2`）生成，作为图片嵌入对应正文；不再默认用飞书原生画板、SVG／HTML 或脚本框图交付，也不先画一版低质量框图。先锁定文案与关系，再逐字逐线验收；只有用户明确要求可编辑原生图或真实统计图需要精确计算时例外。已有有效画板保留；工具不可用时说明，不静默降级；版本未显示时不声称已确认模型版本。图像生成同样要逐字、逐条线验收，不以换工具证明质量提高。

## 嵌入后检查

在最终页面确认图与讲解相邻、尺寸合适、完整显示；按实际宽度再读一遍。图片超过视口时连续覆盖上、中、下部分，区分视口遮挡与真正裁切。保留每张图的目标面截图或渲染证据。

“整体优化全部图”覆盖当前材料全部讲解图；只改其中新补的图不算完成。“只改某图”只覆盖指定图与受影响路径。原始截图、简历与既有有效正文按授权保护，不能把来源图片改画成事实。

## 逐图记录与完成判断

在 `visual_contract.quality_review` 中，每张计划内的图记录：`visual_id`、`reader_question`、`target_width_px`、目标面证据 `evidence`、五项具体观察 `checks`（`meaning`、`logic`、`hierarchy`、`legibility`、`visual_utility`）、`verdict`（`pass`／`revise`／`unverified`）和未解决的 `issues`。

任何必需图为待修或未验证，整体仍未完成。校验器只检查记录完整性和状态，不读取图片、不评美学，也不能保证人工观察真实。不得把校验器的 `ok` 报成“成图质量通过”。独立复核具备权限和能力时可用，但不能替代作者打开最终图与目标页面。
